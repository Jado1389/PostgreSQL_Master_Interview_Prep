Basic

01What is PostgreSQL and how does it differ from MySQL and other relational databases?Easy▼

PostgreSQL is an open-source, object-relational database system with over 35 years of active development. Its core differentiators are:

  • MVCC-native concurrency: Readers never block writers and writers never block readers. This is architectural, not bolted on.
  • Full ACID compliance with SSI: PostgreSQL's SERIALIZABLE level implements Serializable Snapshot Isolation — the only isolation level in any major RDBMS that truly eliminates all concurrency anomalies without heavy locking.
  • Extensibility: You can add custom data types, operators, index access methods, and procedural languages. PostGIS, pgvector, and TimescaleDB are all built on this extension model.
  • SQL standards compliance: PostgreSQL tracks SQL:2016+ closely, including window functions, CTEs, lateral joins, and full-text search as native constructs.

vs MySQL: MySQL (InnoDB) uses a separate undo log for MVCC, meaning old row versions are reconstructed at read time rather than stored in-place. PostgreSQL stores dead tuples in the heap, requiring VACUUM. MySQL's query planner is weaker for complex analytical queries. PostgreSQL supports a richer type system: JSONB with GIN indexing, native arrays, range types, composite types, and domains.

vs Oracle/SQL Server: PostgreSQL lacks Oracle's advanced partitioning maturity and some enterprise features, but is architecturally comparable for OLTP workloads and significantly ahead on extensibility.

Interview framing: Lead with MVCC and extensibility. Mention that PostgreSQL's JSONB with GIN indexes means you can run document-store-style queries inside a relational database without a separate MongoDB instance — a concrete architectural win.
02Explain PostgreSQL's ACID guarantees. How does each property manifest at the implementation level?Easy▼

Atomicity: Implemented via WAL (Write-Ahead Log). When a transaction begins, changes are written to WAL before any data page is modified. If the server crashes mid-transaction, crash recovery replays the WAL and rolls back any incomplete transactions using the XLOG_ABORT record. The key insight is that PostgreSQL never needs an undo log because WAL records contain enough information to redo committed changes and identify incomplete ones.

Consistency: Enforced by the constraint system: NOT NULL, UNIQUE, CHECK, FOREIGN KEY, and EXCLUDE constraints. Constraints can be IMMEDIATE (checked per statement) or DEFERRED (checked at COMMIT), giving application code flexibility. Triggers and rules provide application-level consistency hooks.

Isolation: MVCC provides snapshot isolation for all levels up to REPEATABLE READ. At SERIALIZABLE, PostgreSQL uses Serializable Snapshot Isolation (SSI) — it tracks predicate locks and read/write dependencies between transactions, serializing or aborting those that would produce non-serializable results without using any shared row-level locks.

Durability: WAL records are flushed to durable storage (via fsync) before the commit acknowledgment is sent to the client. synchronous_commit=on (default) enforces this. Setting it to off gives async commits for a performance boost at the cost of losing the last few milliseconds of committed transactions on crash — data is never corrupted, but recent commits may be lost.

Common misconception: synchronous_commit=off does NOT risk data corruption or partial writes. It only risks losing recent committed transactions. The database always remains consistent.
03Describe the PostgreSQL process architecture in detail.Easy▼

PostgreSQL uses a process-per-connection model — no threads. Each client connection forks a dedicated backend process. This provides strong isolation between connections (a crashing backend doesn't affect others) but is expensive in memory (each process ~5-10 MB RSS).

Key processes:

  • postmaster: The parent process. Listens on the TCP port, authenticates new connections, and forks backend processes. Never executes queries itself.
  • Backend process: One per client. Handles the full query lifecycle: parse → analyze → rewrite → plan → execute. Accesses shared_buffers (shared memory), writes WAL, and releases resources on disconnect.
  • Checkpointer: Periodically flushes all dirty shared_buffer pages to disk and writes a checkpoint WAL record. Determines the recovery starting point after a crash.
  • WAL writer: Periodically flushes WAL buffers to disk, reducing latency for backends waiting for WAL flush.
  • Background writer (bgwriter): Proactively writes dirty pages to disk to reduce the I/O burden on checkpointer and backends.
  • Autovacuum launcher + workers: Launches vacuum worker processes when tables accumulate enough dead tuples or approach XID age limits.
  • Stats collector: Collects runtime statistics into pg_stat_* views. Receives UDP messages from backends.
  • WAL archiver: Copies completed WAL segments to the archive location (S3, NFS) when archive_mode=on.
  • Logical replication launcher: Manages logical replication apply workers for subscriptions.

Shared memory regions: shared_buffers (data page cache), WAL buffers, lock table (LWLocks and heavyweight locks), proc array (tracks all active transactions), pg_xact (commit log — records which XIDs committed).

Why this matters: The process model is why connection pooling is non-optional at scale. At 1000 connections, you have 1000 processes each with their own stack, file descriptor set, and memory — that's 5-10 GB of process overhead before any query runs.

05JSON vs JSONB: storage, indexing, and when to use each.Easy▼

JSON stores the exact input text verbatim — whitespace, key order, and duplicate keys preserved. Each read re-parses the text. No GIN indexing possible. Use JSON only when you need to reproduce the exact original text (audit logging, message queue payloads).

JSONB stores a decomposed binary representation — keys are sorted and deduplicated, whitespace stripped. Faster for reads (no re-parsing). Supports two GIN operator classes:

  • jsonb_ops (default): supports @>, <@, ?, ?|, ?&. Larger index.
  • jsonb_path_ops: supports only @> and @@. Smaller and faster for containment queries.
-- JSONB containment query with index CREATE INDEX idx_payload ON events USING gin(payload jsonb_path_ops); SELECT * FROM events WHERE payload @> '{"type":"order","status":"shipped"}'; -- Generated column for frequently-queried JSONB key (avoids TOAST) ALTER TABLE events ADD COLUMN event_type text GENERATED ALWAYS AS (payload->>'type') STORED; CREATE INDEX idx_event_type ON events(event_type);
Pro tip: For frequently-queried JSONB keys that are used in WHERE clauses and JOINs, extract them as generated columns with native type indexes. This is far faster than a GIN index on the full JSONB column for point lookups on a single key.

SQL, Query Execution & Planner

Intermediate
Understanding how PostgreSQL parses, plans, and executes queries is essential for debugging slow queries and writing efficient SQL in interviews.
07What is the PostgreSQL query lifecycle from SQL text to result rows?Med▼

Understanding the full pipeline helps you know where to intervene when a query is slow or incorrect.

  1. Parse: The SQL string is tokenised and parsed into a raw parse tree (AST). Syntax errors are caught here. No catalog lookups yet.
  2. Analyze / Rewrite: The parse tree is semantically analyzed — table and column names are resolved against pg_catalog, types are checked, and the query is rewritten by rule system (e.g., views are expanded inline).
  3. Plan (Optimise): The planner generates candidate execution plans and chooses the one with the lowest estimated cost. It consults pg_statistic (table statistics) to estimate row counts, uses cost parameters (seq_page_cost, cpu_tuple_cost, etc.), and selects join methods and access paths.
  4. Execute: The chosen plan tree is executed by the executor. Nodes are pulled-based (iterator model) — each node pulls rows from its children. Results are streamed to the client.

Prepared statements short-circuit the parse and plan phases on repeated execution. The plan is cached after the first execution (PG 12+ uses generic vs custom plan selection based on cost comparison).

Interview depth: If asked about slow queries, mention that the planner is only as good as its statistics. Stale statistics (from low autovacuum frequency or after bulk loads) cause poor plan choices. ANALYZE refreshes statistics; pg_statistic and pg_stats expose them.
08What are window functions? Explain PARTITION BY, ORDER BY, ROWS/RANGE frames, and practical use cases.Med▼

Window functions compute values across a set of rows related to the current row without collapsing them into one output row (unlike GROUP BY aggregates). They use an OVER() clause.

-- Running total per department, salary rank, month-over-month change SELECT emp_id, dept, salary, hire_date, -- Running sum: all rows from partition start to current row SUM(salary) OVER ( PARTITION BY dept ORDER BY hire_date ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW ) AS running_payroll, -- Dense rank: no gaps on ties DENSE_RANK() OVER (PARTITION BY dept ORDER BY salary DESC) AS pay_rank, -- Previous row value (salary of the person hired before this one in dept) LAG(salary, 1, 0) OVER (PARTITION BY dept ORDER BY hire_date) AS prev_salary FROM employees;

ROWS vs RANGE frames: ROWS counts physical rows (use for running totals). RANGE uses logical value ranges — RANGE BETWEEN INTERVAL '7 days' PRECEDING AND CURRENT ROW gives a rolling 7-day sum, grouping rows with identical ORDER BY values.

Named windows (WINDOW clause) avoid repeating identical OVER definitions and slightly improve readability for complex queries with many window calls.

Key functions: ROW_NUMBER() (unique per partition), RANK() (gaps on ties), DENSE_RANK() (no gaps), NTILE(n) (bucket), LAG/LEAD (adjacent rows), FIRST_VALUE/LAST_VALUE/NTH_VALUE (frame boundary values), all aggregate functions.

09What are CTEs? When are they materialised? What is a recursive CTE?Med▼

A CTE (Common Table Expression) is a named subquery defined with the WITH clause, scoped to a single statement.

Materialisation behaviour: In PostgreSQL 11 and earlier, CTEs were always materialised (executed once, result stored in memory, creating an optimisation fence). From PG 12+, the planner inlines CTEs into the main query by default and may execute them multiple times. Use WITH name AS MATERIALIZED (...) to force the old fence behaviour (useful when the CTE is referenced multiple times and you want the result cached, or when you want to prevent the planner from pushing predicates inside).

-- Recursive CTE: hierarchical org chart traversal WITH RECURSIVE org AS ( -- Anchor: find the root (CEO) SELECT id, name, manager_id, 0 AS depth, name::text AS path FROM employees WHERE manager_id IS NULL UNION ALL -- Recursive: add direct reports SELECT e.id, e.name, e.manager_id, o.depth + 1, o.path || ' > ' || e.name FROM employees e JOIN org o ON e.manager_id = o.id WHERE o.depth < 10 -- cycle guard ) SELECT depth, path, name FROM org ORDER BY path;

Use cases: Org hierarchies, bill-of-materials, category trees, threaded comments, graph traversal (shortest path on small graphs), generating date/integer series.

Pitfall: Recursive CTEs have no built-in cycle detection. Always add a depth counter or path accumulator with a WHERE guard to prevent infinite loops on cyclic data.
10What join methods does the PostgreSQL planner choose from? When is each optimal?Med▼

The planner chooses between three physical join methods based on estimated row counts, available indexes, memory, and data distribution:

11How does EXPLAIN ANALYZE work and what are the key fields to read?Med▼

EXPLAIN shows the planned execution tree without running the query. EXPLAIN ANALYZE executes it and shows actual vs estimated metrics. Always use BUFFERS for production diagnosis:

EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT) SELECT o.id, c.name, o.total FROM orders o JOIN customers c ON o.customer_id = c.id WHERE o.created_at > now() - interval '30 days';

Key fields:

  • cost=0.00..1234.56 — planner's estimate: startup cost .. total cost in arbitrary units
  • rows=500 — planner's estimated row count
  • actual time=0.023..45.6 — actual wall clock time in ms: first row .. last row
  • actual rows=12500 — most important: if this diverges greatly from estimated rows, your statistics are stale
  • loops=10 — node executed this many times (multiply actual time × loops for total)
  • Buffers: hit=450 read=1200 — cache hits vs disk reads. High read = cache miss = cold data or undersized shared_buffers
  • Planning Time / Execution Time — planning overhead is relevant for OLTP queries run thousands of times per second
Workflow: Use explain.dalibo.com to visualise JSON-format EXPLAIN output. Look for the widest nodes (most time) and largest row estimate mismatches. Fix statistics first, then consider indexes.
12What is the difference between all JOIN types, LATERAL JOIN, and set operations?Easy▼

JOIN types: INNER (matching rows only), LEFT OUTER (all left + NULLs for unmatched right), RIGHT OUTER, FULL OUTER (all from both sides), CROSS (Cartesian product, every combination), NATURAL (implicit join on identically-named columns — avoid in production, fragile to schema changes).

LATERAL JOIN allows a subquery in the FROM clause to reference columns from preceding FROM items. The subquery is re-evaluated for each row of the outer relation — like a correlated subquery in the FROM clause.

-- Top 3 orders per customer using LATERAL (no window function needed) SELECT c.id, c.name, recent.order_id, recent.total FROM customers c CROSS JOIN LATERAL ( SELECT id AS order_id, total FROM orders o WHERE o.customer_id = c.id ORDER BY created_at DESC LIMIT 3 ) recent;

Set operations: UNION (deduplicates — expensive sort), UNION ALL (no dedup — always prefer when duplicates are impossible or acceptable), INTERSECT (rows in both), EXCEPT (rows in first not in second). All require compatible column counts and types. UNION ALL is dramatically faster — always use it unless you specifically need deduplication.

13What are generated columns, table inheritance, and partitioning? How do they differ?Med▼

Generated columns (PG 12+): Computed from other columns and stored physically (STORED) or computed on read. Cannot reference other tables or be updated directly. Useful for indexing derived values from JSONB or computing normalised search fields.

ALTER TABLE products ADD COLUMN search_vec tsvector GENERATED ALWAYS AS (to_tsvector('english', name || ' ' || description)) STORED; CREATE INDEX idx_search ON products USING gin(search_vec);

Table inheritance: A child table inherits all columns of its parent. Queries on the parent include rows from all children (unless ONLY is specified). Predates declarative partitioning and is now rarely used for partitioning — use native partitioning instead. Still useful for polymorphic schemas.

Declarative partitioning (PG 10+): A partitioned table is a logical container. Data physically lives in partition tables. Supports RANGE, LIST, and HASH strategies. The planner can prune irrelevant partitions at plan time (static) or runtime (dynamic). Partition-wise JOINs and aggregates can be parallelised across partitions.

Key distinction: Inheritance is for schema polymorphism (like OOP). Partitioning is for data management at scale (query pruning, bulk drop of old data, parallel scans).
14What is the UPSERT pattern? How does ON CONFLICT work and what are its edge cases?Med▼
-- Full upsert with conditional update INSERT INTO user_stats (user_id, login_count, last_seen, first_seen) VALUES ($1, 1, now(), now()) ON CONFLICT (user_id) DO UPDATE SET login_count = user_stats.login_count + EXCLUDED.login_count, last_seen = EXCLUDED.last_seen WHERE user_stats.last_seen < EXCLUDED.last_seen; -- conditional: only update if newer -- Idempotent insert (silently skip duplicates) INSERT INTO processed_events (event_id, processed_at) VALUES ($1, now()) ON CONFLICT (event_id) DO NOTHING;

EXCLUDED is a special table alias referring to the row that was proposed for insertion but conflicted.

Edge cases and gotchas:

  • ON CONFLICT only works on UNIQUE or PRIMARY KEY constraints — not on arbitrary CHECK constraints.
  • If the conflict target is a partial unique index, you must explicitly name the index or its predicate.
  • ON CONFLICT DO UPDATE takes a row-level lock on the conflicting row — can cause contention under high concurrency on the same key.
  • The WHERE clause in DO UPDATE applies after the update expression — it determines whether the update is applied at all.
  • ON CONFLICT DO NOTHING does not increment sequences — the conflicting INSERT is silently dropped.
15What is the PostgreSQL planner cost model? How do statistics influence plan choice?Hard▼

The planner assigns a cost to every candidate plan using a cost model parameterised by configuration variables:

ParameterDefaultMeaning
seq_page_cost1.0Cost of reading one 8 KB page sequentially (baseline unit)
random_page_cost4.0Cost of a random page read. Set to 1.1 on SSD — the biggest single tuning lever for index adoption.
cpu_tuple_cost0.01Cost to process one row
cpu_index_tuple_cost0.005Cost to process one index entry
cpu_operator_cost0.0025Cost to evaluate one operator/function
effective_cache_size4 GBPlanner's assumption about total available cache (OS + PG). Higher = more index scans preferred.

Statistics: The planner reads pg_statistic (exposed as pg_stats) for each column: n_distinct (number of distinct values), most_common_vals and their frequencies, a histogram of value distribution, and correlation (how ordered the column is on disk — affects index scan cost). ANALYZE updates these. The statistics_target per column (default 100) controls histogram bucket count.

-- Increase statistics for a highly selective column ALTER TABLE orders ALTER COLUMN status SET STATISTICS 500; ANALYZE orders; -- Extended statistics for correlated columns (PG 10+) CREATE STATISTICS orders_status_region ON status, region FROM orders; ANALYZE orders;
Extended statistics (CREATE STATISTICS) teach the planner about correlations between columns. Without it, the planner assumes independent columns and under-estimates selectivity of multi-column WHERE clauses — a common cause of nested loop plans on large result sets.

17What causes PostgreSQL to NOT use an index? List every reason.Hard▼

This is a critical production debugging question. A comprehensive answer demonstrates real experience:

  • Low selectivity: The planner estimates a seq scan is cheaper when the query matches more than ~5-15% of rows (varies by table size and random_page_cost setting).
  • Function on indexed column: WHERE UPPER(email) = 'A@B.COM' skips the index on email. Fix: create a functional index on upper(email).
  • Implicit type cast: WHERE id = '123' where id is integer causes implicit text-to-int cast. The planner cannot use the index on the cast expression. Fix: always match parameter types.
  • Stale statistics: After a bulk load or mass delete, statistics may not reflect the new distribution. Run ANALYZE table_name.
  • Non-leading column in composite index: Index on (a, b, c) cannot be used for queries on b alone or c alone without a. It can be used for a, (a,b), and (a,b,c) queries.
  • Leading wildcard LIKE: WHERE name LIKE '%foo%' cannot use a B-tree index. Use GIN with pg_trgm for this pattern.
  • NOT / != operators: Usually forces a seq scan because the result set is expected to be large.
  • Planner cost parameters misconfigured: random_page_cost=4.0 (HDD default) on an SSD database makes index scans look expensive. Set to 1.1 for SSD.
  • Table too small: For tables under ~1000 rows, seq scan is almost always faster than an index scan — the planner correctly ignores the index.
  • enable_indexscan=off: Someone (or a pooler) set this in the session. Check with SHOW enable_indexscan.
-- Diagnose: force index scan to confirm the index could work SET enable_seqscan = off; EXPLAIN ANALYZE SELECT * FROM orders WHERE customer_id = 42; RESET enable_seqscan; -- If cost is still high with index forced, the index isn't selective enough
18Explain partial indexes, covering indexes (INCLUDE), and functional indexes with production examples.Med▼
-- PARTIAL INDEX: only index rows matching the predicate -- 95% of queries touch active users but they're only 5% of the table -- This index is 20x smaller and faster to update than a full index CREATE INDEX idx_users_active_email ON users (email) WHERE status = 'active'; -- Query MUST include the predicate to use this index: SELECT * FROM users WHERE email = $1 AND status = 'active'; -- COVERING INDEX (INCLUDE): store extra columns in leaf pages only -- Enables index-only scan: no heap fetch needed for these queries CREATE INDEX idx_orders_customer_covering ON orders (customer_id, created_at DESC) INCLUDE (total_amount, status); -- This query can be satisfied entirely from the index: SELECT created_at, total_amount, status FROM orders WHERE customer_id = $1 ORDER BY created_at DESC LIMIT 10; -- FUNCTIONAL INDEX: index on expression result -- Enables case-insensitive lookups without UPPER() breaking index CREATE INDEX idx_users_email_lower ON users (lower(email)); CREATE INDEX idx_events_date ON events (date_trunc('day', created_at)); CREATE INDEX idx_payload_type ON events ((payload->>'event_type'));

INCLUDE columns are stored only in B-tree leaf pages — they don't affect the tree structure, sort order, or search key. They enable index-only scans (data read entirely from the index without visiting the heap) but don't consume space in internal tree nodes. The visibility map (VM) must show all pages as all-visible for index-only scans to work — VACUUM maintains this.

19What is CREATE INDEX CONCURRENTLY? What are its failure modes?Med▼

Regular CREATE INDEX takes a ShareLock on the table — blocking writes for the entire build duration (minutes to hours on large tables). CREATE INDEX CONCURRENTLY (CIC) builds the index in the background without blocking writes.

How CIC works internally:

  1. Takes a lightweight ShareUpdateExclusiveLock (allows reads and writes to continue)
  2. Registers the index in pg_index with indisready=false, indisvalid=false
  3. Waits for all existing transactions to complete (snapshot drain)
  4. Scans the table and builds the initial index structure
  5. Waits again for transactions that started before step 4
  6. Scans again to catch changes from step 4-5
  7. Sets indisready=true, indisvalid=true

Failure modes:

  • If any step fails (lock timeout, connection drop, cancellation), PostgreSQL leaves an invalid index in pg_index with indisvalid=false. This index is not used by queries but still costs write overhead on every INSERT/UPDATE/DELETE. You must find and drop it.
  • Cannot run inside a transaction block (BEGIN ... CREATE INDEX CONCURRENTLY ... COMMIT will error).
  • Takes roughly 2-3x longer than a regular index build.
-- Find and clean up invalid indexes SELECT indexrelid::regclass AS index_name, indrelid::regclass AS table_name FROM pg_index WHERE NOT indisvalid; -- Drop the invalid index and retry DROP INDEX CONCURRENTLY schema.index_name; CREATE INDEX CONCURRENTLY index_name ON table_name (column);

MVCC, Transactions & Locking

Advanced
MVCC is PostgreSQL's most important architectural feature. Deep understanding of it is expected at any DBaaS or infrastructure company.
20How does PostgreSQL implement MVCC? Compare it to InnoDB's approach.Hard▼

MVCC (Multi-Version Concurrency Control) allows readers to never block writers and writers to never block readers by maintaining multiple versions of rows simultaneously.

PostgreSQL's approach — tuple versioning in the heap: Every row (tuple) has hidden system columns: xmin (XID that inserted this version), xmax (XID that deleted/updated it, 0 if live), cmin/cmax (command IDs within a transaction), and ctid (physical location: page number, tuple offset). When a row is updated, PostgreSQL inserts a new tuple version with a new xmin and marks the old one with xmax = current XID. Neither version is immediately removed.

Visibility rule: A transaction with snapshot S sees a tuple if: xmin committed before S was taken AND (xmax = 0 OR xmax started after S was taken OR xmax is the same transaction and the command is later). This check is performed inline during every table scan.

InnoDB's approach — undo log: InnoDB stores only the current version of a row in the clustered index. When a row is updated, the old version is written to the undo log. Readers that need an older snapshot reconstruct it by applying undo records backwards until they find a version visible to their snapshot.

DimensionPostgreSQLInnoDB (MySQL)
Where old versions liveIn the heap (table file) as dead tuplesIn the undo log (separate structure)
Read overhead for old dataTuple visibility check (fast)Undo log traversal (slow for very old snapshots)
Write overheadNew tuple written to heapCurrent tuple updated + undo record written
Cleanup mechanismVACUUM reclaims dead tuplesPurge thread cleans undo log
Long transaction impactDead tuples accumulate, VACUUM blockedUndo log grows, read performance degrades
The key insight: PostgreSQL's model is simpler (no undo log) but requires VACUUM as a first-class operational concern. InnoDB's undo log means long-running read transactions can severely degrade write performance as the undo chain grows.
21What are the 4 transaction isolation levels? What anomalies does each prevent in PostgreSQL specifically?Hard▼

PostgreSQL's implementation is stronger than the SQL standard requires at every level:

READ COMMITTED behaviour detail: Each statement gets a fresh snapshot. This means within a single transaction, two identical SELECT queries can return different results if another transaction commits between them. This is the most common source of application-level race conditions.

SSI mechanism: The SSI tracker maintains a graph of read/write dependencies. If the graph would form a dangerous cycle (meaning a serial execution ordering would be impossible), PostgreSQL serializes one transaction with a serialization failure error (SQLSTATE 40001). The application must retry. SSI adds minimal overhead when there are no conflicts — no locks are taken speculatively.

When to use SERIALIZABLE: Financial transfers, inventory systems, any situation where "read then write based on read" correctness is required. The cost is retry logic in your application. For most OLTP workloads, READ COMMITTED with careful application design is sufficient.
22Explain VACUUM, autovacuum, VACUUM FULL, and XID wraparound prevention in depth.Hard▼

What VACUUM does:

  1. Scans the table and identifies dead tuples (xmax is a committed transaction)
  2. Removes dead tuple references from index pages (index vacuuming)
  3. Marks dead tuple space as reusable in the FSM (free space map)
  4. Updates the VM (visibility map) to mark pages as all-visible (enables index-only scans)
  5. Freezes old tuple xmin values to FrozenTransactionId (XID wraparound prevention)
  6. Updates pg_class.relpages and pg_class.reltuples (statistics)

VACUUM FULL: Rewrites the entire table into a new heap file, compacting it. Physically reclaims disk space. Requires an exclusive lock for the entire duration — blocks all reads and writes. Use pg_repack instead for online bloat removal.

Autovacuum triggers: Fires when n_dead_tup > autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor * reltuples. Default: 50 dead tuples + 20% of table. For large tables, 20% means autovacuum fires only after millions of dead tuples accumulate — tune scale_factor down for high-write tables.

XID Wraparound: PostgreSQL uses 32-bit transaction IDs in a modular arithmetic space. Every XID is either "in the past" or "in the future" relative to the current XID with a window of 2 billion. Old tuples must be "frozen" (xmin set to FrozenTransactionId = 2) before they become "in the future" from the perspective of new transactions. If any table has tuples with age > ~2 billion XIDs, PostgreSQL enters emergency shutdown to prevent data corruption (visible in pg_database.datfrozenxid and pg_class.relfrozenxid).

-- Monitor wraparound risk (alert if age > 1.5 billion) SELECT n.nspname, c.relname, age(c.relfrozenxid) AS xid_age, 2000000000 - age(c.relfrozenxid) AS xids_remaining FROM pg_class c JOIN pg_namespace n ON c.relnamespace = n.oid WHERE c.relkind = 'r' AND age(c.relfrozenxid) > 500000000 ORDER BY xid_age DESC LIMIT 10; -- Emergency response: force freeze on a specific table VACUUM FREEZE VERBOSE schema.table_name;
23What are PostgreSQL's lock types? Explain advisory locks and FOR UPDATE / SKIP LOCKED.Hard▼

Lock hierarchy: PostgreSQL has lightweight locks (LWLocks — for internal structures like shared_buffers), heavyweight locks (table-level, row-level), and advisory locks (application-defined).

Table-level locks (weakest to strongest): ACCESS SHARE (SELECT), ROW SHARE (SELECT FOR UPDATE), ROW EXCLUSIVE (INSERT/UPDATE/DELETE), SHARE UPDATE EXCLUSIVE (VACUUM), SHARE (CREATE INDEX), SHARE ROW EXCLUSIVE, EXCLUSIVE, ACCESS EXCLUSIVE (ALTER TABLE, DROP, TRUNCATE — blocks everything including SELECT).

Row-level locks: FOR UPDATE (exclusive row lock), FOR NO KEY UPDATE (weaker exclusive), FOR SHARE (shared), FOR KEY SHARE (weakest shared). Row locks are stored in the tuple's xmax field — no separate lock table entry unless the transaction holds many row locks.

Advisory locks: Application-defined locks using integer keys. Exist only in PostgreSQL's memory — not tied to any table or row. Useful for distributed mutual exclusion (e.g., ensure only one process runs a job at a time across multiple servers connecting to the same DB).

-- Advisory lock: only one worker processes tenant 42 at a time SELECT pg_try_advisory_lock(42); -- returns false if already locked (non-blocking) -- ... do work ... SELECT pg_advisory_unlock(42); -- Queue pattern: SKIP LOCKED for parallel job processing BEGIN; SELECT id, payload FROM job_queue WHERE status = 'pending' ORDER BY priority DESC, created_at LIMIT 10 FOR UPDATE SKIP LOCKED; -- skip rows locked by other workers, no blocking -- process rows, then: UPDATE job_queue SET status = 'done' WHERE id = ANY($processed_ids); COMMIT;
SKIP LOCKED vs NOWAIT: SKIP LOCKED silently skips locked rows and returns the rest. NOWAIT raises an error immediately if any row is locked. Use SKIP LOCKED for job queues, NOWAIT when you want to detect contention and retry.
24What is TOAST and how does it affect query design and performance?Med▼

TOAST (The Oversized-Attribute Storage Technique) handles column values that exceed ~2KB. Since a PostgreSQL page is 8KB and a single value cannot span pages, TOAST compresses and/or chunks large values into a separate TOAST table (named pg_toast_<oid>).

TOAST strategies:

EXTENDEDDefault for text, bytea, JSONB. Compress first; if still too large, store out-of-line in TOAST table.
EXTERNALStore out-of-line but do NOT compress. Faster access to substrings (e.g., substring() operations on text).
MAINCompress in-line first; store out-of-line only if still too large. Stays in main heap longer than EXTENDED.
PLAINNever TOAST. Only usable for small fixed-size types (int, float, bool).

Performance implications:

  • SELECT queries that don't reference TOAST columns never touch the TOAST table — header row in main heap is enough.
  • SELECT * on tables with large JSONB columns triggers TOAST decompression for every row — always SELECT only the columns you need.
  • For frequently-queried scalar values inside JSONB, extract them as generated columns with native types to avoid TOAST overhead entirely.
  • pg_column_size() shows the in-memory size of a value; use it to understand TOAST compression ratios.

25How does WAL work internally? What is an LSN, checkpoint, and full-page write?Hard▼

WAL (Write-Ahead Log) is an append-only sequential log that records every change to data pages before those pages are written to disk. On crash, PostgreSQL replays WAL from the last checkpoint to recover all committed changes.

LSN (Log Sequence Number): A 64-bit monotonically increasing byte offset into the WAL stream. Every WAL record has an LSN. LSNs are used to measure replication lag, identify recovery points, and verify WAL continuity. Use pg_current_wal_lsn() on the primary, pg_last_wal_replay_lsn() on a replica.

Checkpoint: A point where all dirty shared_buffer pages are guaranteed to be written to disk. After a checkpoint, WAL records before the checkpoint LSN are no longer needed for crash recovery (though they may be kept for replication or PITR). Checkpoints are triggered by time (checkpoint_timeout, default 5min) or WAL volume (max_wal_size, default 1GB). The checkpointer process writes pages gradually over checkpoint_completion_target (0.9 = 90% of the interval between checkpoints) to avoid I/O spikes.

Full-page writes (FPW): After every checkpoint, the first modification of each 8 KB page writes the entire page to WAL (not just the change). This protects against partial page writes on crash — the OS might write only part of a page if the server dies mid-write. FPW causes significant WAL volume amplification on write-heavy workloads. It cannot safely be disabled unless your storage guarantees atomic 8 KB writes.

-- Measure replication lag in bytes and seconds SELECT application_name, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), write_lsn)) AS write_lag, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), flush_lsn)) AS flush_lag, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn)) AS replay_lag, write_lag AS write_lag_time, replay_lag AS replay_lag_time FROM pg_stat_replication;

27What is PITR and how do you implement it? What is pgBackRest and why is it preferred over pg_basebackup?Hard▼

PITR (Point-in-Time Recovery) allows restoring a PostgreSQL cluster to any past moment by combining a base backup with a stream of WAL archives. The base backup is a consistent snapshot; replaying WAL from that point forward rebuilds every subsequent state.

# Step 1: postgresql.conf — enable WAL archiving archive_mode = on archive_command = 'pgbackrest --stanza=prod archive-push %p' wal_level = replica # or logical if CDC is needed # Step 2: Take a base backup pgbackrest --stanza=prod backup --type=full # Step 3: Recover to a specific point in time # In postgresql.conf (PG 12+) or recovery.conf (PG 11-): restore_command = 'pgbackrest --stanza=prod archive-get %f "%p"' recovery_target_time = '2025-05-10 14:29:45 UTC' recovery_target_action = 'promote' # or 'pause' to inspect before promoting

pgBackRest advantages over pg_basebackup:

  • Differential / incremental backups: Only changed blocks are backed up after the initial full backup. Dramatically reduces backup time and storage cost for large databases.
  • Parallel backup and restore: Uses multiple streams concurrently for much faster operations on large databases.
  • Delta restore: On restore, only downloads blocks that differ from a local copy — crucial for fast recovery in cloud environments.
  • Retention management: Automatically expires old backups and their WAL based on configurable retention policies.
  • Built-in S3/GCS/Azure Blob support: No separate archive script needed.
  • Backup verification: Can verify backup integrity without a full restore.
28What is Patroni? How does leader election work and how is split-brain prevented?Hard▼

Patroni is a Python-based HA framework for PostgreSQL. It manages a cluster of PostgreSQL nodes (1 leader + N standbys) using a Distributed Configuration Store (DCS) — etcd, Consul, or ZooKeeper — as the authority for leader election.

Leader election mechanism:

  1. Each Patroni agent runs a loop that attempts to hold a leader key in the DCS with a TTL (default 30s).
  2. The current leader refreshes the TTL on every loop iteration. If the leader fails to refresh (crash, network partition), the TTL expires.
  3. Standby agents race to acquire the expired leader key. The one with the highest WAL LSN (most up-to-date replica) wins via a compare-and-swap operation on the DCS.
  4. The winner promotes itself (pg_ctl promote) and updates the DCS with its connection info.
  5. Other standbys detect the new leader and reconfigure streaming replication to follow it.

Split-brain prevention: The DCS is the single source of truth. A node can only act as primary if it holds the leader key in the DCS. Since DCS uses Raft consensus, only one node can hold the key at a time, even under network partition — as long as the DCS quorum is intact. A primary that loses DCS connectivity cannot renew its TTL and will eventually be demoted (Patroni can be configured to use pg_ctl stop on DCS loss). The old primary, when it recovers, uses pg_rewind to align its WAL with the new primary before rejoining as a standby.

DCS quorum requirement: etcd requires a majority (N/2 + 1). With 3 nodes: can tolerate 1 failure. With 5 nodes: can tolerate 2 failures. Never run a 2-node DCS — it provides zero fault tolerance.
29What is logical decoding and CDC? How do you set up Debezium for PostgreSQL?Hard▼

Logical decoding is PostgreSQL's mechanism for converting raw WAL records into a stream of logical changes (row-level INSERT/UPDATE/DELETE events with old and new values). It uses output plugins — pgoutput is the built-in plugin (used by native logical replication and Debezium >= 1.x), wal2json is a popular JSON-format plugin.

Operational risks with CDC: A stalled Debezium consumer causes the replication slot to retain WAL indefinitely. Set max_slot_wal_keep_size = '10GB' (PG 13+) to cap this. 34When and how do you use table partitioning? What are the operational considerations?Hard▼

When to partition: Tables above 50-100 GB where queries always filter on a specific column (time, region, tenant), or where you need to bulk-delete old data by dropping partitions (infinitely faster than DELETE). Do not over-partition — tables under 10 GB with random access patterns see no benefit and increased planning overhead.

-- RANGE partitioning: monthly event log CREATE TABLE events ( id bigserial, tenant_id int, event_time timestamptz NOT NULL, payload jsonb ) PARTITION BY RANGE (event_time); -- Auto-create partitions with pg_partman SELECT partman.create_parent( p_parent_table := 'public.events', p_control := 'event_time', p_interval := '1 month', p_premake := 3 -- pre-create 3 future partitions ); -- Detach and drop old partitions (faster than DELETE, immediate reclaim) ALTER TABLE events DETACH PARTITION events_2024_01 CONCURRENTLY; DROP TABLE events_2024_01;

Operational considerations:

  • Always include the partition key in the WHERE clause — otherwise the planner scans all partitions.
  • Each partition is a separate heap with its own FSM, VM, and autovacuum tracking. VACUUM must run on each partition independently.
  • Foreign keys to/from partitioned tables have limitations in older PG versions (resolved in PG 12+).
  • Unique constraints on a partitioned table must include the partition key.
  • Partition-wise JOINs (two partitioned tables joined on the partition key) can be very efficient — enable with enable_partition_wise_join=on.

36How do you perform a zero-downtime major version upgrade?Hard▼

Strategy 1: Logical replication upgrade (recommended, <5 min downtime)

  1. Spin up a new cluster with the target PostgreSQL version
  2. Apply schema to new cluster: pg_dump --schema-only | psql
  3. Enable logical replication on source: wal_level=logical, CREATE PUBLICATION all_pub FOR ALL TABLES
  4. Create subscription on target: initial data sync + ongoing CDC
  5. Monitor lag until consistently <1 second
  6. Maintenance window: stop writes on source, wait for lag=0, flip application connection strings to new cluster
  7. Decommission old cluster

Strategy 2: pg_upgrade --link (near-zero downtime)

Uses hard links to avoid copying data files. Only the WAL, system catalogs, and control file are rewritten. For a 1 TB database, upgrade time is minutes rather than hours. Requires stopping the old server. Use pg_upgrade --check first to validate compatibility without changing anything.

Post-upgrade actions (both strategies):

  • Run ANALYZE on all tables — statistics format may differ between versions
  • Monitor query plans for regressions in the first 24-48 hours
  • Run vacuumdb --all --analyze if upgrading from very old versions
  • Update extensions: ALTER EXTENSION name UPDATE
37What is pg_repack and when is it better than VACUUM FULL?Med▼

VACUUM FULL rewrites the entire table but requires an ACCESS EXCLUSIVE lock for the entire duration — blocking all reads and writes. On a large production table, this can mean hours of complete downtime.

pg_repack reclaims bloat online with only a brief lock at the end:

  1. Creates a shadow copy of the table
  2. Applies ongoing DML changes to the shadow copy via triggers
  3. When shadow copy is fully caught up, takes a brief ACCESS EXCLUSIVE lock (usually under 1 second) to swap the old and new tables
  4. Drops the old table and triggers
# Online bloat removal (no extended downtime) pg_repack --host=localhost --username=postgres \ --dbname=mydb --table=bloated_orders # Also rebuilds indexes — useful after heavy DELETE/UPDATE churn pg_repack --dbname=mydb --table=orders --only-indexes

When VACUUM FULL is still appropriate: Maintenance windows where downtime is acceptable, tables with very high write rates (pg_repack trigger overhead can be significant), or when pg_repack is unavailable in a managed service.

Alternative: On cloud managed services (RDS, Cloud SQL, Azure) where pg_repack may not be installed, use CLUSTER table USING index (rewrites table in index order, requires lock) or create a new table with CREATE TABLE ... AS SELECT, then rename. Both require a maintenance window.
38What are triggers and stored procedures in PostgreSQL? When should you use them vs application-layer logic?Med▼

Triggers: Functions automatically executed before or after (or instead of) INSERT, UPDATE, DELETE, or TRUNCATE events on a table. Row-level triggers fire per affected row; statement-level triggers fire once per statement.

-- Audit trigger: record every change with before/after values CREATE OR REPLACE FUNCTION audit_trigger() RETURNS trigger LANGUAGE plpgsql AS $$ BEGIN INSERT INTO audit_log (table_name, operation, old_data, new_data, changed_by, changed_at) VALUES (TG_TABLE_NAME, TG_OP, CASE WHEN TG_OP != 'INSERT' THEN row_to_json(OLD) END, CASE WHEN TG_OP != 'DELETE' THEN row_to_json(NEW) END, current_user, now()); RETURN NEW; END; $$; CREATE TRIGGER orders_audit AFTER INSERT OR UPDATE OR DELETE ON orders FOR EACH ROW EXECUTE FUNCTION audit_trigger();

Use triggers for: Audit logging, derived column maintenance (where generated columns are insufficient), enforcing complex cross-table constraints, notifying downstream systems via NOTIFY.

Avoid triggers for: Business logic that belongs in the application (hard to test, invisible to ORM), performance-critical paths (triggers add overhead to every DML), any logic that requires external service calls (triggers cannot make HTTP requests).

Stored procedures (PROCEDURE, not FUNCTION): PG 11+ supports procedures that can run transaction control (COMMIT/ROLLBACK) inside. Functions cannot. Use procedures for long-running batch operations that need to commit incrementally.

41What is idle-in-transaction, how do you detect it, and why is it a production hazard?Med▼

A connection in idle in transaction state has an open transaction but is not actively executing. It holds open a snapshot (preventing VACUUM from cleaning dead tuples visible only to that snapshot) and may hold row or table locks blocking other queries. A single idle-in-transaction connection on a heavily-written table can cause dead tuple accumulation equivalent to a VACUUM failure.

-- Detect idle-in-transaction connections older than 2 minutes SELECT pid, usename, application_name, client_addr, state, wait_event_type, wait_event, extract(epoch from now() - xact_start)::int AS tx_age_s, left(query, 100) AS last_query FROM pg_stat_activity WHERE state = 'idle in transaction' AND xact_start < now() - interval '2 minutes' ORDER BY tx_age_s DESC;

Prevention: Set idle_in_transaction_session_timeout = 30000 (30s in ms) in postgresql.conf — PostgreSQL automatically terminates any connection that stays idle-in-transaction beyond this threshold. Also set per-role statement_timeout to catch runaway queries before they go idle.

Common cause: Application code that opens a transaction, makes an external HTTP call or sleeps, and only commits afterward. Any external call inside a transaction is a production risk. Design your code so transactions are opened only immediately before the SQL operations and committed/rolled back synchronously.

RDS-01What are Parameter Groups and how do you tune memory parameters on RDS?Med▼

Parameter Groups are RDS's replacement for postgresql.conf. They are versioned (a PG 15 Parameter Group cannot be applied to a PG 14 instance) and can be shared across multiple instances. Changes to dynamic parameters take effect immediately; static parameters require an instance reboot.

RDS does not accept absolute byte values for memory parameters. Instead, it uses a formula syntax referencing DBInstanceClassMemory (the instance's total RAM in bytes):

-- Parameter Group formula examples shared_buffers = {DBInstanceClassMemory/32768} -- 25% of RAM (in 8KB pages) effective_cache_size = {DBInstanceClassMemory/10922} -- 75% of RAM (in 8KB pages) work_mem = 65536 -- 64 MB (fixed, set carefully) maintenance_work_mem = 2097152 -- 2 GB checkpoint_completion_target = 0.9 random_page_cost = 1.1 -- SSD storage (critical) effective_io_concurrency = 200 -- SSD

Key operational notes: The default RDS Parameter Group is read-only. Always create a custom Parameter Group before launch. Apply it to the instance before any application load to avoid a reboot during production hours. Changes to Parameter Groups are applied immediately to new connections but existing connections may keep old settings until they reconnect.

Most impactful single change: Setting random_page_cost=1.1 on any RDS instance backed by gp2/gp3/io1 storage. The default of 4.0 causes the planner to avoid index scans on SSD where they would be fast, leading to seq scans and slower query plans.
RDS-02How does RDS Multi-AZ work? What is the failover process and how do you minimise RTO?Med▼

RDS Multi-AZ maintains a synchronous physical standby in a different Availability Zone. Every write is committed to both the primary and standby storage before acknowledging to the application. The standby does not serve reads — it is purely for failover.

Failover trigger conditions: AZ failure, underlying hardware failure, OS patching (planned), instance class change, manual failover via AWS Console or reboot --force-failover.

Failover process:

  1. RDS detects primary failure via internal health checks (every ~10 seconds)
  2. Promotes the standby to primary
  3. Updates the DNS CNAME of the cluster endpoint to point to the new primary's address
  4. Total time: 60–120 seconds (dominated by DNS TTL propagation to clients)

Minimising application RTO:

  • Use the RDS-provided endpoint hostname (never hard-code IP addresses — they change on failover)
  • Configure connection pool TTL to <300s so stale connections to the old IP are recycled
  • Use DNS-aware connection poolers (PgBouncer or RDS Proxy reconnect to new IP automatically)
  • Implement retry logic in the application for connection errors (SQLSTATE 08*)
  • For RTO <35s: use Multi-AZ Cluster (PG 14+) with quorum writes instead of standard Multi-AZ
RDS-03What is RDS Performance Insights and how do you use it to identify bottlenecks?Med▼

Performance Insights measures database load as Average Active Sessions (AAS) — the average number of sessions actively working at any moment, broken down by wait event type. It is sampled at 1-second intervals and stored for 7 days (free) or up to 2 years (paid).

Reading the dashboard:

  • The horizontal line on the AAS chart equals the number of vCPUs. Consistently above this line means the database is overloaded.
  • Wait event types: CPU (query is running, not waiting), io/DataFileRead (buffer cache miss), Lock (waiting for a row or table lock), LWLock:BufferMapping (shared_buffers contention), IPC (parallel query coordination)
  • Drill into the Top SQL tab to find which queries are causing the highest AAS

Diagnostic patterns:

  • High CPU + slow queries → add indexes, rewrite queries
  • High io/DataFileRead → working set larger than shared_buffers, consider instance upgrade or gp3 storage tuning
  • High Lock waits → contention on hot rows, connection pileup, or idle-in-transaction connections holding locks
  • Spiky AAS at regular intervals → checkpoint I/O, autovacuum on large tables, scheduled batch jobs
RDS-04What is RDS Proxy and when should you use it over PgBouncer?Med▼

RDS Proxy is AWS's fully managed database proxy that sits between your application and RDS/Aurora. It maintains a warm pool of server-side connections and multiplexes application connections over them using transaction-level pooling.

Key advantages over self-managed PgBouncer:

  • Failover resilience: During an RDS/Aurora failover, RDS Proxy maintains client connections — it pauses queries, reconnects to the new primary, and resumes. Applications see a brief pause (~5s) rather than connection errors.
  • IAM integration: Authenticates clients via IAM tokens (no stored database passwords in application config). Integrates with Secrets Manager for automatic credential rotation.
  • Serverless friendly: Eliminates connection explosion from Lambda functions, which create new DB connections per invocation. Lambda + RDS without a proxy is a known anti-pattern.
  • Zero ops overhead: No EC2 instance to manage, patch, or scale.

Limitations vs PgBouncer: RDS Proxy pins connections (falls back to session mode) when it detects SET commands, temporary tables, advisory locks, or LISTEN/NOTIFY — negating the pooling benefit for those sessions. PgBouncer gives more fine-grained control. RDS Proxy costs ~$0.015/hr per vCPU of the DB instance.

AUR-01How is Aurora's storage architecture fundamentally different from RDS PostgreSQL?Hard▼

RDS PostgreSQL runs standard, unmodified PostgreSQL on EBS volumes. The write path is: PostgreSQL writes WAL to EBS → dirty pages are written to EBS. This is two network hops through the virtualization stack. EBS replication within an AZ provides durability; Multi-AZ mirrors the EBS volume to another AZ synchronously.

Aurora's fundamental re-architecture: Compute (the PostgreSQL engine) and storage are completely separate services. The storage layer is a distributed, multi-AZ system. Aurora's PostgreSQL engine has been modified to send only redo log records to the storage service — the storage nodes apply the redo to construct page versions locally. Pages are never written from compute to storage. This inversion — storage doing the "storage engine" work — is the key innovation.

Consequences of this architecture:

  • 5x less I/O: No full-page writes (the storage layer handles partial writes), no double-write buffer, no background writer flushing dirty pages. Only the redo log goes over the network.
  • Near-instant crash recovery: The storage layer already has the latest state from the redo log. There is no WAL replay needed — the page version is current at the storage layer.
  • Fast failover: All replicas already share the same storage volume. Promoting a replica to writer means it just starts accepting writes — no data copy, no WAL stream catchup. This is why Aurora failover is ~30s vs RDS ~90s.
  • Low replica lag: Read replicas don't receive a WAL stream over the network. They read the same shared storage, with only a small in-memory log buffer to apply. Typical replica lag: <20ms.
AUR-02Where does Aurora sit on CAP theorem and PACELC? What are the consistency implications for reads from replicas?Hard▼

CAP Theorem: Aurora is a CP system. When fewer than 4 of 6 storage nodes are available (a quorum failure), Aurora stops accepting writes rather than risk inconsistency. It sacrifices Availability to preserve Consistency under Partition.

PACELC: Under Partitions: C over A. Else (normal operation): L (Low Latency) over C (full Consistency) for reads from read replicas. Reads from the writer endpoint are always strongly consistent. Reads from read replicas may return data that is up to ~20ms stale (the replica's in-memory log buffer delay).

Practical implications:

  • If your application requires reading immediately after a write (read-your-own-writes), always route those reads to the writer endpoint, not a reader replica.
  • For analytics queries, dashboards, and reporting — reader replicas are appropriate and offload the writer significantly.
  • Aurora's replica consistency is substantially stronger than streaming replication read replicas (which can lag 50–500ms under load) because the storage is shared.
Interview depth point: Aurora's storage quorum (4 of 6) means it can tolerate losing 2 storage nodes simultaneously without data loss or write stoppage. Losing 3 storage nodes causes write stoppage but the data already written is safe (3 copies remain). This is a much stronger durability guarantee than a single EBS volume with Multi-AZ mirroring.

AUR-04Aurora Global Database: architecture, RPO/RTO, write forwarding, and when to use it.Med▼

Aurora Global Database replicates at the storage layer (not the SQL layer) using Aurora's purpose-built replication technology. This gives it sub-second cross-region lag regardless of write rate — a significant advantage over logical replication which can lag under heavy write loads.

Architecture: 1 primary region (read-write) + up to 5 secondary regions (read-only, each with their own Aurora cluster). The primary region's storage service continuously streams log records to secondary storage services. Secondary regions serve reads locally to reduce latency for global users.

RPO: typically <1 second. RTO: <1 minute for managed planned failover. For unplanned regional failure, RTO is typically under 1 minute with recent Aurora versions.

Write forwarding: Applications in secondary regions can send writes to a secondary endpoint; Aurora silently proxies these writes to the primary region over the Global Database replication channel. The application doesn't need to know where the primary is. Adds one cross-region round-trip to write latency (~50–200ms depending on distance).

When to use: Active-passive DR with RPO <1s; global applications where reads should be served from the nearest region; compliance scenarios requiring cross-region data replication with minimal lag.

AUR-05How does Aurora Serverless v2 scale? What are its minimum capacity and cold start characteristics?Med▼

Aurora Serverless v2 (ASv2) measures capacity in Aurora Capacity Units (ACUs), where 1 ACU represents approximately 2 GB of memory and proportional CPU and network. Capacity scales between a configurable minimum (as low as 0.5 ACU) and maximum (up to 128 ACU) in increments as small as 0.5 ACU.

Scaling behaviour: ASv2 monitors CPU utilisation, database connections, and query queue depth. It scales up within seconds by allocating additional capacity from a pre-warmed pool — there is no cold start delay comparable to v1 (which took several minutes). Scale-down is gradual over minutes to avoid oscillation.

Minimum 0.5 ACU: ASv2 does not scale to zero. A cluster at minimum capacity still runs ~$0.03/hr. For true zero-cost idle periods, consider Aurora Serverless v1 (now deprecated) or stop the cluster manually (downtime required to restart). For development databases, use RDS stop/start instead.

When ASv2 is cost-effective: Workloads with significant variance between peak and baseline (e.g., 10x peak/baseline ratio). If your baseline is consistently 50%+ of peak, a fixed-size instance is usually cheaper. ASv2 is particularly valuable for multi-tenant SaaS where aggregate load grows linearly with tenant count.

ADB-02How does AlloyDB's columnar engine work and what queries benefit from it?Hard▼

AlloyDB maintains two in-memory data stores simultaneously: the standard PostgreSQL row-oriented buffer pool and a columnar cache. A machine learning model monitors column access patterns and automatically populates frequently-scanned columns into the columnar cache in compressed columnar format.

Query routing: AlloyDB's modified query planner evaluates the cost of using the columnar cache vs the row store for each query. For analytical patterns (aggregations, GROUP BY, range scans over many rows, analytical JOINs), the columnar path is chosen automatically. For OLTP patterns (point lookups, small result sets, index-driven queries), the row store is used. The planner can split execution: columnar for the scan and aggregation, row store for the final row-level fetch.

Queries that benefit:

  • Aggregations over large ranges: SELECT SUM(revenue), AVG(margin) FROM orders WHERE created_at BETWEEN ...
  • Analytical GROUP BY: SELECT region, product_type, SUM(qty) FROM sales GROUP BY region, product_type
  • Wide table scans with column projection: reading 3 columns from a 50-column table
  • Time-series analytics, cohort analysis, business intelligence queries

Queries that do NOT benefit: Primary key lookups, small range scans, queries already served from B-tree index scans, INSERT/UPDATE/DELETE operations.

ADB-03How do you implement vector similarity search in AlloyDB using pgvector and ScaNN?Hard▼

-- Enable extensions CREATE EXTENSION vector; CREATE EXTENSION google_ml_integration; -- for Vertex AI embedding calls -- Create table with vector column CREATE TABLE product_embeddings ( product_id bigint PRIMARY KEY, description text, embedding vector(768) -- 768-dim for text-embedding-gecko ); -- Generate embeddings using Vertex AI directly from SQL INSERT INTO product_embeddings (product_id, description, embedding) SELECT id, description, embedding('textembedding-gecko@003', description) FROM products; -- Create ScaNN index (faster than ivfflat for large datasets) CREATE INDEX product_scann_idx ON product_embeddings USING scann(embedding cosine) WITH (num_leaves = 100); -- Semantic similarity search SELECT product_id, description, 1 - (embedding <=> embedding('textembedding-gecko@003', 'wireless noise cancelling headphones')) AS similarity FROM product_embeddings ORDER BY embedding <=> embedding('textembedding-gecko@003', 'wireless noise cancelling headphones') LIMIT 10;
ScaNN vs ivfflat: ScaNN uses Google's proprietary quantisation and search algorithms, achieving higher recall at the same query speed compared to ivfflat. For production AlloyDB workloads with millions of vectors, ScaNN is the preferred choice.

ADB-06How does AlloyDB's intelligent autovacuum differ from standard PostgreSQL autovacuum?Med▼

Standard PostgreSQL autovacuum uses static thresholds (autovacuum_vacuum_scale_factor and autovacuum_vacuum_threshold) configured globally or per-table. These static values are a poor fit for tables with widely varying write patterns — a table that has high insert-only traffic might not need vacuum as urgently as a table with heavy UPDATE/DELETE churn.

AlloyDB's adaptive autovacuum uses a machine learning model that observes each table's historical write patterns (insert rate, update rate, delete rate, query patterns) and dynamically adjusts vacuum frequency and aggressiveness per table. Tables with heavy UPDATE workloads get vacuumed more aggressively; insert-only tables are vacuumed less frequently, reducing I/O overhead.

The result is reduced DBA intervention for autovacuum tuning and more consistent table health across workloads that vary over time (e.g., day/night traffic patterns or seasonal load spikes). This is particularly valuable in multi-tenant environments where each tenant's table has different write characteristics.

AZ-03How does zone-redundant HA work on Flexible Server? What is the RTO and RPO?Med▼

Zone-redundant HA on Flexible Server uses synchronous streaming replication between a primary VM in one Availability Zone and a standby VM in a different zone within the same region. Unlike Cloud SQL (which uses a shared regional disk), Flexible Server uses actual PostgreSQL streaming replication — the standby maintains a continuously-updated replica of the primary.

Failover process:

  1. Azure monitors the primary via internal health checks every ~10 seconds
  2. On failure detection, the standby is promoted to primary
  3. DNS of the server endpoint is updated to point to the new primary (in the standby's zone)
  4. The old primary, when it recovers, becomes the new standby

RTO: approximately 60–120 seconds (health check interval + promotion + DNS propagation). RPO: approximately 0–60 seconds — synchronous replication reduces data loss but does not guarantee zero RPO in all failure scenarios (the standby must have received and acknowledged the last commit).

Same-zone HA (alternative): Primary and standby in the same zone. Faster failover (~30s) since there is no cross-zone latency for the health check round-trip. Lower cost (no cross-zone data transfer charges). Lower availability SLA (98.99% vs 99.99% for zone-redundant). Use same-zone HA for dev/test; use zone-redundant for production.

AZ-10How do you implement pgvector for AI workloads on Azure Flexible Server?Med▼

pgvector is supported on Azure Flexible Server (PG 14+). Azure also integrates with Azure OpenAI Service, allowing you to generate embeddings directly from your application and store/query them in Flexible Server without a separate vector database.

-- Enable pgvector extension CREATE EXTENSION vector; -- Create a table with vector column CREATE TABLE document_chunks ( id bigserial PRIMARY KEY, document_id bigint REFERENCES documents(id), chunk_text text, embedding vector(1536), -- 1536 for text-embedding-ada-002 created_at timestamptz DEFAULT now() ); -- IVFFlat index for approximate nearest neighbour search CREATE INDEX ON document_chunks USING ivfflat(embedding vector_cosine_ops) WITH (lists = 100); -- HNSW index (PG 16 + pgvector 0.5+): better recall, higher build time CREATE INDEX ON document_chunks USING hnsw(embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64); -- Semantic search: find top 5 similar chunks SELECT id, chunk_text, 1 - (embedding <=> $1::vector) AS cosine_similarity FROM document_chunks ORDER BY embedding <=> $1::vector LIMIT 5;

Architecture pattern (RAG on Azure): Azure OpenAI generates embeddings → stored in Flexible Server (pgvector) → semantic search retrieves relevant chunks → chunks + query sent to Azure OpenAI GPT-4 for response generation. This keeps all data within Azure's trust boundary, satisfying enterprise data governance requirements.

ivfflat vs HNSW: HNSW gives better recall at query time but has a longer build time and uses more memory. For production: use HNSW if you can afford the build time. For quick prototyping or smaller datasets (<1M vectors), ivfflat is fine. Neither is as fast as AlloyDB's ScaNN for very large vector collections.
AZ-11How do you use read replicas on Flexible Server? What are their limitations?Med▼

Read replicas on Flexible Server use PostgreSQL streaming replication (physical). Up to 5 replicas can be created, in the same region or cross-region. Replicas are read-only and can be promoted to standalone servers (breaking replication permanently).

# Create a read replica az postgres flexible-server replica create \ --resource-group myRG \ --source-server myserver \ --name myserver-replica-1 \ --location eastus2 # can be same or different region

Use cases: Offload read-heavy analytical queries from the primary. Provide lower-latency reads for geographically distributed users. Pre-production data access for data science teams without touching production.

Limitations:

  • Replication uses asynchronous streaming — replicas can lag under heavy write loads on the primary (unlike Aurora's storage-shared replicas)
  • Replicas inherit the primary's server parameter configuration; some parameters cannot be changed independently
  • Promotion to standalone is permanent — cannot re-establish replication to the original primary
  • Zone-redundant HA standby is separate from read replicas — you cannot use the HA standby for read traffic (it is passive for HA purposes only)
  • Cross-region replicas incur data transfer charges for the replication traffic
